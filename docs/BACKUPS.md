# Регламент резервного копирования и восстановления базы данных PostgreSQL

> **Статус документа**: Черновик регламента для передачи юристу / техническому директору перед коммерческим запуском сервиса.

---

## 1. Автоматические резервные копии (Managed PostgreSQL)

При размещении базы данных у облачного провайдера (Yandex Cloud Managed Service for PostgreSQL / Selectel Managed Databases) резервное копирование настраивается на уровне платформы:
1. **Ежедневный полный снимок (Full Backup)**: создается автоматически раз в сутки во время технологического окна с минимальной нагрузкой (например, 03:00–05:00 по московскому времени).
2. **Журналирование упреждающей записи (Write-Ahead Logging, WAL)**: непрерывно архивируется в изолированное объектное S3-хранилище провайдера.
3. **Глубина хранения резервных копий**:
   - `[срок хранения резервных копий в днях: заполняет владелец, например 7 / 14 / 30 дней]`.
   - По истечении установленного срока старые копии автоматически удаляются и перезаписываются в процессе ротации.

---

## 2. Восстановление на момент времени (Point-in-Time Recovery, PITR)

Наличие непрерывных WAL-архивов позволяет восстановить состояние базы данных на любую произвольную секунду в пределах окна хранения:
1. В консоли провайдера или через Terraform/CLI выбирается точка восстановления (timestamp).
2. Разворачивается отдельный временный инстанс PostgreSQL из снапшота и накатываются WAL-журналы до указанной секунды.
3. Проверяется целостность данных и соответствие схемы.
4. Выполняется переключение приложения (Switchover) на восстановленный кластер путем обновления переменной `DATABASE_URL`.

---

## 3. Регламент и тестирование восстановления (Disaster Recovery Drill)

Для подтверждения работоспособности бэкапов устанавливается следующий регламент:
1. **Периодичность учебных восстановлений**: не реже одного раза в квартал на изолированном staging-контуре.
2. **Критерии успеха проверки**:
   - Время полного восстановления (RTO) не превышает регламентное значение (например, 30 минут).
   - Потери данных (RPO) при сбое не превышают интервала фиксации WAL (обычно менее 1–5 минут).
   - Запуск проверочного набора тестов (`pytest backend/tests/test_repo_scenarios.py`) на восстановленной БД завершается без ошибок.

---

## 4. Особенности удаления данных (Право на забвение vs Резервные копии)

> [!WARNING]
> **Важное уведомление для DPO и владельца сервиса:**
> При запросе пользователя на удаление аккаунта или пары (`DELETE /couple`) персональные данные стираются из рабочей базы данных немедленно.
> Однако физические следы данных остаются в ранее созданных резервных копиях до момента их естественной циклической ротации и безвозвратной перезаписи.
> 
> Рекомендации для политики конфиденциальности:
> - Явно зафиксировать в пользовательском соглашении: «При удалении аккаунта данные удаляются из операционной базы незамедлительно, а из архивных резервных копий — в течение срока ротации резервных копий (`[срок ротации бэкапов: заполняет владелец]`)».
> - При восстановлении базы данных из старого бэкапа обязательно запускать скрипт сверки журнала удалений (`audit_deletions`) для повторного удаления данных пользователей, запросивших забвение.
