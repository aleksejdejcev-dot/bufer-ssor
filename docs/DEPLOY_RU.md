# Руководство по развертыванию проекта «Буфер Ссор» (PostgreSQL)

> **Статус документа**: Черновик технического руководства для администратора и юриста перед коммерческим запуском сервиса.

---

## 1. Локальный запуск (Docker Compose)

Для локальной разработки и сквозного тестирования используется локальный контейнер PostgreSQL:

```bash
# 1. Запуск контейнера PostgreSQL и автоматическое применение миграций:
./scripts/db_up.sh

# 2. Проверка состояния:
docker compose ps

# 3. Применение миграций вручную (при добавлении новых файлов):
python3 scripts/migrate.py --database-url "postgresql://buffer_admin:buffer_dev_pass@127.0.0.1:5432/buffer_ssor"

# 4. Остановка локальной базы данных:
./scripts/db_down.sh

# 5. Полный сброс тестовых данных (с удалением тома pgdata/):
./scripts/db_reset.sh
```

## 2. Развертывание в облачной инфраструктуре

Для промышленной эксплуатации используется управляемый кластер PostgreSQL (Managed Service for PostgreSQL) и виртуальный сервер приложения (VPS):
- **СУБД**: Кластер PostgreSQL версии 15 или 16 (Multi-AZ / Master-Replica).
- **Размещение**: База данных размещена у [провайдер, регион: заполняет владелец].
- **Сеть**: Доступ к порту 5432/6432 разрешен только с IP-адресов серверов приложения через Security Groups / Firewall.

### 2.1. Требования к TLS-шифрованию
В промышленном окружении (`ENVIRONMENT=production`) подключение к базе данных выполняется исключительно по зашифрованному каналу TLS:
- `DB_SSLMODE`: значение должно быть `require`, `verify-ca` или `verify-full`. Режим `disable` разрешен только для локального Docker и блокирует старт приложения в production.
- `DB_SSL_ROOT_CERT`: при использовании самоподписанных сертификатов провайдера путь к CA-сертификату передается через переменную `DB_SSL_ROOT_CERT`.

### 2.2. Ролевая модель доступа к БД
В базе данных разделены полномочия:
1. **Роль `migrator`**:
   - Владелец схемы данных.
   - Обладает правами на выполнение DDL-операций (`CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX`).
   - Используется исключительно при накатывании миграций (`scripts/migrate.py`).
2. **Роль `app_user`**:
   - Рабочая учетная запись приложения.
   - Обладает только правами DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) на прикладные таблицы и `EXECUTE` на хранимые функции.
   - Не имеет прав суперпользователя и прав на изменение схемы (DDL).
   - Приложение на старте валидирует отсутствие суперпользовательских прав (`rolsuper=false`).

## 3. Миграции базы данных

Миграции хранятся в каталоге `db/migrations/*.sql` и нумеруются по порядку (`001_init_schema.sql`, `002_payments_and_retention.sql`, `003_roles_and_permissions.sql`).

Раннер `scripts/migrate.py`:
- Создает служебную таблицу `schema_migrations`.
- Проверяет уже примененные версии.
- Выполняет каждый новый файл в отдельной транзакции.
- Является полностью идемпотентным (повторный запуск безопасен и ничего не меняет).

## 4. Фоновая очистка данных (Retention Scheduler)

Очистка устаревших данных выполняется встроенным планировщиком приложения (`backend/retention_scheduler.py`) без внешних расширений (pg_cron).
- Для координации между репликами используется распределенная блокировка `pg_try_advisory_lock`.
- Очищаются:
  - Временные зашифрованные исходники `pending_inputs` (по истечении TTL 48 часов).
  - Карточки и общий результат удаляются после просмотра обоими участниками либо при ближайшем цикле очистки (по умолчанию в течение часа).
  - Устаревшие счетчики `rate_limits`.
  - Непринятые приглашения в пары (старше 48 часов).
  - Платежные записи по истечении `PAYMENT_RETENTION_YEARS` (только если значение явно задано владельцем).
